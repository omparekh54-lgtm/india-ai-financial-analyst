# Phases 25–30 — Production Release Acceptance

This document defines the final deployment-readiness block for the India-first AI Financial Analyst. It is intentionally fail-closed: software readiness cannot substitute for genuine corpus coverage, source approval, real-company evidence, production credentials, or an actually deployed API.

## Phase 25 — Genuine production corpus

Production requires the existing listing-aware agent readiness contract to pass for the real NSE EQ universe. The read-only operator manifest is:

```bash
python scripts/run_production_corpus_manifest.py --min-nse-eq-securities 1000
```

The manifest reports corpus coverage, all 16 agent readiness states, blocking agents, and real-data next actions. It never inserts sample or synthetic data. The authoritative mutation path remains `bootstrap_production_research_corpus.py` and its existing market, financial and peer-metric stages.

A release remains blocked until the corpus gate is genuinely green.

## Phase 26 — Representative real-company end-to-end acceptance

A production release must prove that persisted real research has passed through the evidence architecture, not merely that unit tests pass.

```bash
export REAL_COMPANY_ACCEPTANCE_JOB_IDS="<job-uuid-1>,<job-uuid-2>,..."
python scripts/run_real_company_acceptance.py
```

Default acceptance requires at least five distinct real securities across at least four populated sectors. Each supplied job must be completed and linked to a real security, contain a persisted report, have completed Agent 15 (`evidence_cross_validation`) and Agent 16 (`chief_analyst_research_composer`) runs, contain validated claims, and contain claim-to-evidence/source links. Non-production provenance markers fail the gate.

No acceptance job or evidence is generated by the gate itself.

## Phase 27 — Provider and integration activation controls

```bash
python scripts/run_provider_activation_gate.py
```

The provider gate validates operator feature flags, credential presence and FREE_ONLY eligibility without exposing secret values. Enabled integrations fail closed when required credentials are incomplete. Paid routes remain ineligible while `FREE_ONLY=true`.

The result is explicitly labelled configuration/policy verification. Credential presence is not represented as proof that a third-party endpoint, quota, licence or broker session is live.

Optional integrations remain disabled unless the production operator intentionally activates them.

## Phase 28 — Production deployment package

`deploy/docker-compose.production.yml` is the checked-in production package for API and workers. It includes:

- API container health checking against `/health`.
- init handling and graceful stop windows for long-running services.
- separate research, official-feed and live-market worker processes.
- a `maintenance` profile containing the one-shot research-calibration job.
- no embedded application/provider secrets.

Calibration is intentionally not presented as a daemon until a real scheduler is chosen. Run the maintenance job explicitly or through an approved scheduler:

```bash
docker compose -f deploy/docker-compose.production.yml --profile maintenance run --rm research-calibration
```

## Phase 29 — Security, load, operations and compliance acceptance

The final release path reuses the hardened acceptance components rather than inventing parallel checks:

- `run_production_preflight.py` — production config/database preflight.
- `run_operations_health_report.py` — queues, ingestion, official feeds, evidence and calibration health.
- `run_commercial_launch_gate.py` — source-use approval and commercial launch gate.
- `run_deployment_smoke.py` — authenticated GET-only deployed API smoke.
- `verify_auth_isolation.py` — two-user ownership/isolation verification.
- `run_load_probe.py` — bounded read-only load acceptance.

Supabase security and performance advisors should also be reviewed after DDL changes and before launch. INFO-only unused-index notices on new/empty tables are not treated as evidence of a production defect by themselves.

## Phase 30 — Final release/launch gate

The only release-level command is:

```bash
python scripts/run_production_release_gate.py \
  --api-base-url "https://api.example.com" \
  --job-id "<owner-job-uuid>"
```

The protected GitHub workflow `.github/workflows/production-release-gate.yml` is the preferred production execution path.

The stage order is fixed:

1. preflight
2. corpus readiness
3. representative real-company acceptance
4. provider activation policy
5. operations health
6. commercial/source approval
7. deployed API smoke
8. auth isolation
9. bounded load probe

Execution stops at the first failed stage. `release_ready=true` is emitted only if every stage passes.

## Secrets and cost policy

Access tokens, provider API keys, broker client secrets and encryption keys remain environment/GitHub Environment secrets. They are never passed as release-gate CLI arguments or written to result artifacts.

`FREE_ONLY=true` is the default launch policy. No silent paid fallback is permitted.

## What this block does not fake

The repository may be fully implemented and CI-green while the final release gate remains red. That is expected when any external prerequisite is incomplete, including:

- full genuine NSE corpus coverage,
- representative completed real-company research,
- provider credentials for an explicitly enabled integration,
- commercial source/licensing approval references,
- production HTTPS deployment,
- production authentication test users/tokens.

Those are launch prerequisites, not values that software should manufacture.
